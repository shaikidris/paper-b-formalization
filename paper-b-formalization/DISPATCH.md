# Work allocation and coordination

This is an agent-ready assignment plan. **No workers are assigned or running for it.** `assigned_agent` is null throughout the tracker. Owner roles identify responsibility; they are not a report of live activity.

## First packet: settle the interfaces

The coordinator owns PB0.3 and PB0.4. An infrastructure role handles PB0.5. Deliver a supported environment and actual elaborated Challenge before mathematical proof work. The reviewer checks fixed-program quantifiers, visible cost semantics, nonvacuous input conditions and the literal Theorem 3.2 correspondence. Record approval of the exact typed contract rather than inferring it from general enthusiasm for the project.

The environment pilot may inspect libraries and build a minimal nonproof specimen. It does not justify importing the whole old research library or claiming a certified root.

## First proof wave

Once the typed contract is approved, graph and resource work establish PB1.1–PB1.5, with PB4.1 providing the operational model before its consumers. Freeze semantic and primitive-cost interfaces before independent consumers start. Then use at most three concurrent proof workers plus a coordinator, if execution is authorized to use agents:

- **Kernel owner:** PB2.1–PB2.7. Deliver split/deletion correspondence, bounded flow and decomposition, SCC/path labels, arbitrary-target membership, proper-cut tests and actual kernel construction cost.
- **Scheduler owner:** PB3.1–PB3.4. Deliver a concrete answer-vector state machine and invariants, initially consuming only the frozen kernel interface. No invented whole-query oracle or silent failure to scan original targets.
- **Resource owner:** PB4.1 first, then PB4.2–PB4.4, with early review of PB1.5/PB2.7. Deliver primitive refinement, event charges and peak-memory proofs. Resource costs are not postponed until every data structure is already fixed.
- **Coordinator/reviewer:** join PB4.5–PB4.6, check file ownership and signature consistency, and run PB9.1–PB9.2. Avoid adding convenience imports unrelated to these roots.

The kernel and scheduler can proceed separately only where their signatures are stable. A later interface change invalidates affected handoffs and requires rechecking consumers.

## Later independent packets

After the core, choose work by approved release objective: exact sharing (PB5); common-anchor/localization/chains (PB6); guarded equivalence and baselines (PB8.1–PB8.3); constructive reductions (PB7); canonical summaries and selectors (PB8.4–PB8.5); conditional/application composition (PB8.6–PB8.8). They are not all prerequisites of the first release.

## One-writer rule

`tasks.json.module_owners` assigns one writer to every proposed file. Resource reviewers return an exact lemma/interface or reviewed patch for integration by the file owner. They do not concurrently edit `Kernel.lean` or `Interning.lean`. Coordinator integration uses a bounded batch and rebuilds the owner and selected roots.

No agent creates another module or changes Challenge without the admission/change-control gate. New mathematical routes stay in the research workspace until checked. Width and weighted-cover tasks PB6.8–PB6.11 use their own optional owner modules and do not enter the first-release core. Root signatures, costs and ownership are shared contracts rather than each worker's local interpretation.

## Required handoff

Every handoff names the task and selected-root obligation; exact exported declaration types; source and dependency hashes; changed files; owner/root build commands and results; axiom/dependency audit; resource assumptions still open; the downstream consumer; and one of proved, conditional, implemented-only, or blocked-on-a-named-input. It includes the obligation burn-down change or exact theorem-type narrowing.

A status message saying only “tests pass”, “many lemmas added”, or “agent still working” is not a completed handoff. Do not report a proof worker as active based on a historical task name. When agents are used, reconcile the actual live inventory and last handoff with the tracker.

## Updates and escalation

Keep proof status, execution status and mathematical coverage separate. Each completed batch updates evidence and regenerates views. After two batches without closing or narrowing a selected-root obligation, stop that route and make an explicit architecture decision. Preserve the prior source and evidence rather than relabelling an unresolved task complete.
